## 検出と対応

### 1. 管理 API が未認証で 200 を返していた（Medium / 修正済）

**事象:** 認証なしで叩いた管理 API のうち 2 本が `401` ではなく `200` を返した。

**影響:** 返却内容はいずれも空であり、データの漏洩は無かった。
一方で「未認証」と「権限不足」を区別できないため、監視側でアクセス異常を検知できず、
クライアント実装も誤った分岐を組み込む余地があった。

**原因:** 認証ヘルパーが未認証時にも「未認証を表すオブジェクト」を返す設計だったため、
呼び出し側の「ユーザーが居なければ弾く」というガードが**常に偽**になり、素通りしていた。
同種のガードが管理 API・管理ページ全体に存在した（実害が出ていたのは 2 本）。

**対応:**
- 認証ヘルパーの戻り値を「未認証なら `null`」に変更し、ガード漏れを型で検出できるようにした
- 全呼び出し側を null チェックに統一

**検証:** ローカル環境に対して同じプローブを実行し、管理 API 全 15 本が `401` を返すことを確認。

### 2. 未認証時の応答が 401 と 403 で不統一（Low / 修正済）

**事象:** 未認証アクセスの応答が `401` と `403` に混在していた（11 本）。

**影響:** 認可は成立しており（いずれも拒否）、情報漏洩は無い。
ただし監視・クライアント実装の観点で「ログインすれば見られる」と「権限が足りない」を
区別できない。

**対応:** 未認証は `401`、権限不足は `403` に統一した。

### 3. Content Security Policy ヘッダ未設定（Medium / 未対応）

**事象:** 公開ページ・ログインページで CSP ヘッダが返っていない。

**影響:** XSS が混入した場合に、ブラウザ側の多層防御が働かない。

**未対応の理由:** リッチテキストエディタと Next.js のインラインスクリプトが前提のため、
厳格な CSP を入れると管理画面が壊れる。nonce ベースの CSP か、
`frame-ancestors 'none'; base-uri 'self'; object-src 'none'` に限定した
段階的な導入が必要で、アプリ側の改修を伴う。
（`X-Frame-Options: DENY` は既に付与されており、クリックジャッキングは防げている）

### 4. クロスオリジン系ヘッダの不足（Low / 受容）

COEP / COOP / CORP が未設定または緩い値。3rd party の iframe・画像配信との共存を
優先しており、厳格値にすると管理画面の機能が壊れるため現状の値を受容する。

### 5. レート制限が無い（Low / 保留）

**事象:** ログインページへ 10 連続リクエストしても制限がかからない。

**影響:** 総当たり攻撃の抑止は認証基盤（Cognito）側の保護に依存している。
アプリ／CDN 層での制限は無い。

**判断:** WAF を関連付けていない構成（`wafMode: none`）のため。
導入する場合は WAF のレートベースルールを追加する。

### 6. Big Redirect（Low / 受容）

ログインリダイレクトの Location ヘッダ長に対する指摘。機密情報は含まない。

### 7. 公開 API の CORS ワイルドカード（Medium / 意図した設計）

**事象:** 公開 API が `Access-Control-Allow-Origin: *` を返す。

**判断:** 公開 API は任意の利用者サイトに埋め込みスクリプト／HTML を配信する仕様であり、
オリジンを限定すると機能が成立しない。返却するのは公開済みコンテンツのみで、
認証情報も送らない（`*` では credentials は送信されない）。

**再評価条件:** 認証や非公開データを返すエンドポイントを追加した時点で、
オリジン制限とこの判断を見直す。

## 修正の本番反映と再スキャン

修正を本番へ反映した後、同じスクリプトで再検査した。

| 検査 | 修正前 | 修正後 |
|---|---|---|
| 管理 API 認可プローブ | PASS 17 / WARN 13 / FAIL 2 | **PASS 30 / WARN 2 / FAIL 0** |
| ZAP Baseline | High 0 / Medium 4 / Low 11 | High 0 / Medium 4 / Low 11 |

残る WARN は「CSP 未設定」と「レート制限なし」の 2 件のみで、
いずれも § 3・§ 5 に記載した保留項目。
Baseline の数値が変わらないのは、指摘の大半が CloudFront の
レスポンスヘッダ設定に関するもので、アプリコードの修正対象ではないため。
なお公開 API は今回変更しておらず、API Scan の再実行は省略している。

### 補足: 書き込み系で観測される 403 の内訳

CloudFront OAC は、リクエストボディの SHA256 と `x-amz-content-sha256`
が一致しないリクエストを**エッジで 403** にする。実クライアントは署名
ユーティリティでこのヘッダを付けるため、通常はアプリまで到達する。

検査スクリプトも同じヘッダを送るよう修正して再測定し、
アプリ層が `401` を返すことを確認した。
ヘッダを付けないと「アプリが認可で弾いた」のか「エッジが署名で弾いた」のか
区別できず、**認可漏れがあっても PASS に見える**ため注意が必要。

## 誤検知として除外した項目

| ルール | 除外理由 |
|---|---|
| SQL Injection | データストアは NoSQL のみで SQL を組み立てない |
| Proxy Disclosure | CDN 配信であることは公開情報 |
| Unexpected Content-Type | 大半が外部ドメイン由来、信号が弱い |
| Cross-Domain Misconfiguration | 上記 7. のとおり意図した設計 |

根拠は `scripts/dast/zap.conf` にコメントで残している。

## 再発防止

- 認可ガードは「未認証なら null」を返す型に統一し、書き忘れをコンパイル時に検出する
- 管理 API を追加したら `scripts/dast/admin-probe.sh` の一覧に追加する
  （追加しないと検査対象外になる）
- 未認証は `401`、権限不足は `403` を守る（監視の判定条件になるため）
