# DAST 運用ルール

`why:`
本番しか環境が無いため、能動スキャンは「実行するほど負荷とキャッシュ汚染が積み上がる」
一方で、やらなければ認可漏れに気づけない。実行頻度・公開範囲・修正フローを
先に決めておかないと、属人的な運用になって継続しない。

## 1. スキャン頻度

| 種別 | スクリプト | 頻度 | 担当判断のポイント |
|---|---|---|---|
| 認可プローブ（未認証） | `admin-probe.sh` | 月次 | FAIL が 1 件でもあれば最優先で修正 |
| 受動スキャン | `zap-baseline.sh` | 週次 | Medium 以上の増加を監視 |
| 公開 API 能動スキャン | `zap-api-scan.sh` | 月次 | High が出たら修正まで公開サマリを出さない |
| 全体能動スキャン | `zap-full-scan.sh` | 四半期 | 実行後に必ず invalidation |

定期実行は現時点では手動（カレンダー登録）。CI 化する場合は下記 § 6。

## 2. 実行前チェックリスト

- [ ] 対象が本番であることを認識している（`TARGET_BASE` の確認）
- [ ] アクセスが少ない時間帯か（Full Scan のみ必須）
- [ ] `SITE_ID` / `CONTENT_TYPE` が実在するテナントを指しているか
- [ ] Docker が起動しているか

## 3. 実行後チェックリスト

- [ ] `zap-reports/*.json` を `summarize.mjs` に通した
- [ ] High / Medium を triage した（修正 or 誤検知の根拠を `zap.conf` に記載）
- [ ] Full Scan の場合、CloudFront の invalidation を実行した
- [ ] サマリを `docs/security/reports/YYYY-MM-DD.md` に追加した
- [ ] 修正した場合、その旨と理由をコミットメッセージに残した

## 4. レポート公開ポリシー

公開するのは **`docs/security/reports/` のサマリのみ**。

公開してよい:

- 重要度別の件数
- 検出ルール名（ZAP のルール名）
- 修正状況（修正済 / 未対応 / 誤検知）
- 再発防止の一般論

公開してはいけない:

- エンドポイントパス・クエリパラメータ名
- 攻撃ペイロード・レスポンス本文・スクリーンショット
- ホスト名（CloudFront ドメイン）
- テナント ID
- 未修正脆弱性の再現手順

理由: 未修正の詳細を公開することは「攻撃の手引き」を配布するのと同じで、
修正前の開示は脆弱性の悪用リスクを上げるだけになる。
生レポート（HTML/JSON）は `zap-reports/`（`.gitignore` 済み）に留める。

## 5. 修正フロー

1. `admin-probe.sh` / ZAP の指摘を再現する（ローカルで `npm run dev` して確認）
2. コードを修正する
3. `TARGET_BASE=http://localhost:9002 ./scripts/dast/admin-probe.sh` で再現しないことを確認
4. デプロイする
5. 本番に対して同じスクリプトを再実行し、解消を確認する
6. サマリを更新する

`why 手順 3 を挟むか:`
本番にデプロイしてから気づくと、修正が効いていない状態が本番に残る。
ローカルで「修正前は FAIL / 修正後は PASS」を確認しておくと、デプロイ後の
判定が確実になる。

## 6. 現時点で「未対応」と判断している項目

| 項目 | 判断 | 根拠 |
|---|---|---|
| CSP ヘッダ未設定 | 保留 | TinyMCE / Next.js のインラインスクリプトを考慮すると nonce ベースの CSP が必要で、アプリ側の改修を伴う。`frame-ancestors` のみの最小 CSP から段階導入する |
| COEP / COOP / CORP の値 | 受容 | 3rd party iframe（エディタ・画像配信）との共存を優先。厳格値にすると機能が壊れる |
| レート制限なし | 保留 | CloudFront に WAF を関連付けていない（`wafMode: none`）。ログイン試行の制限は Cognito 側の保護に依存している状態。必要になった時点で WAF のレートベースルールを追加する |
| 公開 API の CORS ワイルドカード | 受容 | 任意の利用者サイトに埋め込む仕様。返すのは公開済みコンテンツのみで credentials は送らない。**非公開データを返すエンドポイントを追加した時点で再評価する** |
| Big Redirect Detected | 受容 | ログインリダイレクトの Location ヘッダ長に対する指摘。機密は含まない |

上記は「脆弱性ではない / 対応コストが高い」と判断したものであり、
**判断を変える条件**（例: WAF 導入、CSP 対応、エディタ変更）が発生したら再評価する。

## 7. 定期実行の自動化（将来）

現状は手動。自動化する場合の推奨:

- GitHub Actions の `schedule` + `workflow_dispatch` で **baseline のみ**を週次実行
- Active Scan は負荷とキャッシュ汚染があるため自動化しない（手動トリガに限定）
- レポートは artifact に保存（public リポジトリでは artifact も要注意）
