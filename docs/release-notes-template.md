# リリースノートのテンプレート

> **why:** リリースノートは「何が変わったか」だけでなく「利用者が何を押せば反映されるか」まで書かないと、配布済みイメージの利用者は動けない。newcleus の反映経路は `setup1b`（CDK デプロイ）に集約されているため、**構造変更の有無を最初に明示する**ことを型として固定する。

---

## 使い方

1. このファイルをコピーして本文を作る（リポジトリには残さず、`gh release create --notes-file` に渡す）
2. `vX.Y.Z` を実際のバージョンに置き換える
3. 「アップデート手順」は `docs/update.md` §6 の型から転記する（コマンドを手で書き起こさない）
4. リリース後、`docs/wsl.md` §11 の `gh release create` のバージョン表記も更新する

---

## テンプレート本文

```markdown
## vX.Y.Z リリースノート

**リリース日:** YYYY-MM-DD

---

### このリリースの位置づけ

- 変更の種類: **アプリコードのみ** / **CDK（インフラ）変更あり** / **ドキュメントのみ**
- ダウンタイム: あり / なし（Lambda のイメージ更新は atomic）
- 所要時間の目安: ファイル差し替え X 分 + デプロイ Y 分

---

### 変更内容

#### 1. <変更の要約>

- **症状 / 背景:** 利用者から見て何が困っていたか
- **原因:** どの実装が原因だったか
- **対応:** どのファイルをどう変えたか
- **影響範囲:** どの画面・API に影響するか（影響しない範囲も書く）

---

### アップデート手順（既存ユーザー）

> 構造変更が無いリリースでも、コード変更は Lambda に反映する必要がある。

1. WSL 内でファイルを差し替える（`docs/update.md` 3-1）

   ```bash
   (
     set -euo pipefail
     curl -fsSL --retry 3 -o /tmp/fetch-app.sh \
       https://raw.githubusercontent.com/okamoto53515606/newcleus/main/setup/scripts/fetch-app.sh
     bash -n /tmp/fetch-app.sh
     bash /tmp/fetch-app.sh --dir "$HOME/newcleus" --update --build
   )
   ```

2. セットアップ画面を起動し直す

   ```powershell
   wsl -d newcleus -u ubuntu -- bash -i /home/ubuntu/newcleus/setup/start.sh
   ```

3. セットアップ画面 → `setup1b` →「CDK デプロイを実行（サイト公開）」
   - **CDK 変更が無いリリースでも、アプリコードの反映にはこの操作が必要**（現状 `/ops` が無いため）
4. 管理画面のサイドバー下部が `vX.Y.Z` になっていることを確認
5. 公開サイトを開き直す（HTML は CloudFront でキャッシュされないため、キャッシュ削除は不要）

### 検証結果

- `npm run typecheck`: 成功 / 失敗
- `npm run build`: 成功 / 失敗
- `cdk diff NewcleusInfraStack`: 差分なし / 差分あり（内容）
- 動作確認した内容（ログイン、記事一覧、公開サイト等）

---

### npm audit

- メイン（`--omit=dev`）: 0 件 / n 件（内容と実行時影響の有無）
- setup: 0 件 / n 件

---

### 既知の制約

- アプリコードのみの更新でも `setup1b`（Docker ビルド込み）が必要
- 画像は `/media/*` がキャッシュされるため、同じファイル名での差し替えは古い画像が残る
